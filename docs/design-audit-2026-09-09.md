# FormaBot 项目设计与失败场景审查

> 历史调研/审查记录：下文结论对应当时的范围与基线，不作为当前已实现能力。最新事实见 [状态矩阵](status.md)，整改顺序见 [执行计划](../tasks/plan.md)。本轮未重新联网核验历史第三方来源。

审查日期：2026-09-09。代码基线：`f5d20b216f2579f84ea1834d573dc9af660c2c1a`。本次只交付分析、反例脚本与证据，不修改产品实现，不涉及 UI 视觉评判。

**结论：FormaBot 已经有可实际运行的本地成员与群协作原型，但尚不适合把重要用户目录、真实登录账号或需要严格审批的业务交给它持续自主执行。** 障碍主要在宿主执行规则，而非界面或是否接通模型。真实反例证明，路径沙盒存在硬链接绕过，停止不能回收全部后代进程，人工纠正不影响当前执行，成员结果待确认时整轮仍可能标为完成。

这一结论不否定已记录的真实模型成功链路，也不把尚未开发的生图、上传下载、正式发行当成实现错误。成功链路证明“能做成一次”，本报告检查“在什么条件下会做错、越界或丢失控制”。

## 2. 我对现有系统的理解

实际链路是：Electron 主进程读取全局模型配置与空间授权 → `ConversationSession` 管理一轮内存队列 → 每个成员任务启动一个 Node sidecar → sidecar 调用 DeepSeek Harness → 自定义工具经带随机令牌的回环 HTTP 桥回到主进程 → 文件/Bash 经 Seatbelt 执行，浏览器使用 Electron WebContentsView，团队工具直接更新 SQLite。

这不是多个长期驻留且各自持有独立模型、账号和记忆的 Agent 进程。当前成员主要是持久身份与职责，执行时共用一次捕获的全局模型配置，逐任务创建 Harness，按当前会话最近历史重新构造输入。

| 边界 | 当前实现 | 已有价值 / 当前限制 |
| --- | --- | --- |
| 配置 | `settings.json` + safeStorage；临时文件 rename 保存 | Key 不回显，失败保留配置；只有一份全局模型配置 |
| 空间授权 | `tasks.sqlite`，规范路径 + device/inode | 不按成员重复授权，目录替换可失效；不等于账号/外发业务授权 |
| 成员与群 | `workbench.sqlite` 的 conversations/teams/messages | 持久建队、按群读取历史；角色和业务规则主要是文本 |
| 调度 | 一份全局 activeSession/running；内存 FIFO，人工请求 unshift | 支持实际派发与停止入口；不是带依赖、版本和审批的任务图 |
| 工具 | 桥接时核验授权，原生文件/Bash 工具关闭 | 对正常路径和符号链接有效；后代进程、硬链接与网络边界不完整 |
| 浏览器 | 每空间一个持久 partition，共用当前页面 | 不导入个人 profile；没有成员/账号/任务级使用范围 |
| 产物 | write/edit 返回路径，成员正常结束后登记到消息 | 能预览实际文件；没有不可变版本、独立登记与完成证据 |
| 恢复 | 启动时把 queued/running 标记 interrupted | 避免自动重放；没有副作用回执、检查点和明确续跑流程 |

值得保留的基础：主框架 IPC 身份校验、renderer 的隔离、系统密钥存储、不自动加载用户个人运行配置、工具桥随机令牌、逐工具授权检查、建队事务、崩溃后不盲目重放。这些是后续修复的基础，不建议无证据更换 Harness 或重写整个应用。

## 3. 缺陷与失败场景

P1 表示在扩大真实数据或业务使用前应修复；P2 表示应纳入后续功能阶段。未列 P0：已发现严重问题都有具体触发条件，不把它们描述为每次启动必然失败。

### F01 · P1 · 已有硬链接可让 Bash 读写空间外文件

**实测，E01。** 在授权空间外创建标记文件，再在空间内创建指向它的硬链接。`read` 正确拒绝硬链接，但 `bash: cat linked.txt` 返回空间外标记，`printf ... > linked.txt` 实际改写了外部原文件。

证据：[local.ts:20–24](../src/tools/local.ts#L20) 允许工作空间路径读写、拒绝新建 link；[file-worker.ts:10](../src/tools/file-worker.ts#L10) 的 `nlink > 1` 检查仅存在于文件 worker。Bash 完全绕过该检查。实测原文件从 `AUDIT_OUTSIDE_ONLY` 变成 `AUDIT_CHANGED`。

前提是同一文件系统内已经存在硬链接；未证明模型可在当前沙盒里创建跨界硬链接，也未针对用户真实文件尝试。导入、已有目录结构或外部进程创建的链接即可触发。原有测试只覆盖路径和符号链接，因此继续通过。

建议：把工作目录映射与真实文件身份隔离作为执行层门槛；已有链接扫描只能降低风险，不能单独解决竞态和运行中新增链接。评估受控副本/独立文件系统或更强隔离，在验证通过前限制通用 Bash 使用真实敏感目录。验收同时覆盖 read/write/edit/Bash、已有硬链接和运行中变化。

### F02 · P1 · 停止进程组不等于停止所有任务后代

**实测，E02/E03。** 两种有界反例均写出了停止后的标记文件：

1. Bash 启动重定向标准输入输出的后台任务，父命令正常返回；随后 abort，后台仍写文件。
2. Bash 内的 Node 启动 `detached:true` 子进程；父命令还在运行时 abort，独立进程组中的子进程继续写文件。

证据：[local.ts:35–50](../src/tools/local.ts#L35) 只杀 `-child.pid`，父进程 close 后清除定时器和 abort 监听；[task-host.ts:40–46](../src/runtime/task-host.ts#L40) 同样按进程组处理。现有停止测试使用 `sleep 30`，没有覆盖脱离进程组和父进程提前结束。

影响：即使任务变成 stopped 或已撤销授权，已启动后代仍可能改文件或访问网络。下一成员串行开始后，上一个成员的后台工作可能仍在运行，所以“串行队列”也不充分保证文件与账号没有并发冲突。浏览器另有正常完成后继续活动的问题，见 F07。

建议：把任务拥有的进程和资源放入能持续追踪、回收的执行容器/监督机制；不得以单个 shell 退出判定所有动作完成。停止状态应在资源收敛后确认。验收包括正常返回遗留后台、脱离会话、超时、撤销、退出应用，以及停止后持续观察无写入。

### F03 · P1 · 外部副作用与业务审批只靠提示词

**静态确认 + 本地浏览器实测 E10。** 工具桥仅检查“当前空间是否授权”，没有检查外发动作、目标账号、目的地址、内容版本或用户批准记录：[task-host.ts:20–24](../src/runtime/task-host.ts#L20)。Bash 沙盒明确允许 `network*`：[local.ts:24](../src/tools/local.ts#L24)。浏览器任意 selector 的 click 可提交表单：[browser.ts:40](../src/tools/browser.ts#L40)。本地测试没有提供独立动作授权，点击仍产生 POST。

“外部发布需用户明确指令”写在 [task-sidecar.ts:16](../src/runtime/task-sidecar.ts#L16) 和工具描述里，属于模型行为约束，没有执行层证据可判定这次提交是否获得授权。浏览器上传尚未实现并不能阻止文本发布、表单提交或 Bash HTTP 请求。

反例：任务是“读页面并草拟回复”，页面内容诱导模型点击提交；或某成员要求另一成员发送文件。只要模型服从，宿主没有第二层拒绝机制。**本次没有做真实模型提示注入成功率试验，也没有对外提交。** 这里确认的是宿主没有阻挡能力，不是声称某个模型一定被骗。

建议：独立记录业务动作授权，绑定目标、账号、动作、内容/文件版本和时效；由执行工具强制校验。通用 Bash 网络和浏览器点击如果可以绕过，新增一个“发布工具”也不足以解决问题。工作空间基础授权继续长期复用，业务审批不应伪装成重复空间弹窗。

### F04 · P1 · 人工追加不是当前任务纠正，且多条追加按倒序执行

**调度实测 E04 + 静态确认。** 当前任务的 prompt 不含后来的人类纠正，旧动作仍执行；连续输入“取消旧版”“最新要求”，实际顺序为“旧任务 → 最新要求 → 取消旧版”。

证据：[main.ts:113–115](../src/desktop/main.ts#L113) 只调用 `human`；[conversation-session.ts:30](../src/runtime/conversation-session.ts#L30) 对每条人类指令 `unshift`；正在 `await execute` 的任务没有接收更新的通道，prompt 已在 [82–85 行](../src/runtime/conversation-session.ts#L82) 固定。工具桥也不核对指令版本。

反例：写入前用户说“改为草稿，别覆盖原文件”，当前成员仍按旧 prompt 调工具。后续成员看到新历史可能自行纠正，但这不是即时生效保证。原有 live-group-control 只确认“追加进入队列并可全部停止”，没有证明追加能改变当前任务。

另一个范围问题：在会话 A 执行时给会话 B 发消息，两者加入同一个 activeSession，停止入口停掉整轮，两者没有独立运行归属与控制器；见 [main.ts:113–139](../src/desktop/main.ts#L113)。不是历史混入，但会造成控制和根任务归属混淆。

建议：区分追加新任务、修改当前任务、停止；为任务记录指令版本，在下一次副作用工具前检查版本。更新后重规划或真实 steer 当前运行。人工消息保持 FIFO，取消/替换有明确对象；每个会话或根任务具有独立生命周期。验收必须检查旧写入没有发生，而不只检查消息已保存。

### F05 · P1 · 成员结果未确认，整轮仍可显示“已完成”

**调度实测 E05 + 静态确认。** 一个群任务只返回文字而不调用 `task_result`，成员状态为 `responded`，但 `session.run()` 正常 resolve。主进程随即把根任务写为 completed，界面显示“已完成”。

证据：[conversation-session.ts:87–93](../src/runtime/conversation-session.ts#L87)、[main.ts:137](../src/desktop/main.ts#L137)、[renderer.ts:61–69](../src/desktop/renderer.ts#L61)。私聊在没有回执时直接 completed；有回执时也只验证 status/summary 的格式，不验证交付物或工具证据：[conversation-session.ts:39](../src/runtime/conversation-session.ts#L39)。

反例：模型回复“还需要材料”，但未报 blocked；或报 completed，却没有目标文件。宿主不能据此证明用户目标完成。不能要求所有闲聊都必须有文件，但应根据任务的交付约定判断。

建议：将模型回合结束、消息已处理、任务完成分开；根任务状态由子任务和待确认项汇总。交付类任务绑定可验证条件；未确认时明确保持待确认。模型自述只是证据来源之一。

### F06 · P1 · 分工没有前置依赖、批准节点和版本约束

**调度实测 E12 + 静态确认。** 构造“前置研究 → 后续写作”，研究回执 blocked 后，调度仍启动写作，再安排主管汇总；整轮最后才报失败。写作任务指令即使写着“必须等待研究完成和用户批准”，队列也不会因此停住。

证据：[conversation-session.ts:55–59](../src/runtime/conversation-session.ts#L55) 仅记录成员和文字指令；[87–93 行](../src/runtime/conversation-session.ts#L87) 失败只是设置 `failed=true`，循环继续；数据库 [workbench.ts:12](../src/state/workbench.ts#L12) 没有依赖、批准和输入版本。测试仅证明被派发，未让模型执行写作，不能声称模型必然忽略前置条件。

这直接影响 [建队 fixture 验收 4](../tests/fixtures/team-from-document/README.md)：未批准 Brief 时主笔不启动，批准绑定具体版本，不得由主管伪造。目前职责文本和群消息不能落实这一约束。

建议：保留自由群消息，但生产任务增加最小依赖关系与 `waiting_input / waiting_approval`，批准绑定输入版本与真实用户操作，前置受阻只暂停依赖它的下游；独立任务可继续。不需要先造复杂流程编辑器。

### F07 · P1（真实账号接入前）· 浏览器共享身份与任务生命周期未分开

**实测 E09/E11 + 静态确认。** 每个空间只有一个基于空间路径 hash 的浏览器 partition，所有成员和会话共用，见 [main.ts:96/126–130](../src/desktop/main.ts#L96)、[browser.ts:20–24](../src/tools/browser.ts#L20)。在本地设置构造 Cookie，关闭页面再打开，Cookie 仍是 `ACCOUNT_A`。持久登录是需要的能力，但没有“谁能用哪个账号做什么”的额外范围。

反例：研究成员登录了只允许读数据的账号，其他成员拿到同一登录上下文；或用户在成员执行中用右栏地址栏导航，下一次 read/click 面对的页面已经改变。[browser-control](../src/desktop/main.ts#L97) 不与 Agent 页面操作串行协调。

浏览器工具返回后会移除 abort 监听：[browser.ts:13–15](../src/tools/browser.ts#L13)。实测打开延迟 POST 的本地页面，工具返回后 abort，页面仍提交。正常任务结束只 abort 工具控制器，未显式关闭/冻结页面；页面保留的同时脚本也继续运行。

**边界：App 的 stop-task 会显式 close 浏览器，因此 E11 不证明停止按钮后浏览器仍活着；它证明单次工具/正常任务结束不是网页副作用结束。**

建议：浏览器身份独立于空间授权，支持明确共享的账号使用范围；将页面控制权、任务动作期和用户手动操作分开。任务结束保留预览时明确处理活动脚本与未完成请求。验收覆盖成员切换、账号切换、重启、人工导航竞争以及结束后活动。

### F08 · P2 · 产物登记不独立，旧交付链接可指向新内容

**实测 E08 + 静态确认。** 登记 VERSION_1 后覆盖同一路径为 VERSION_2，旧消息仍获准预览，读到 VERSION_2。数据库保存路径数组，没有内容 hash 或版本：[workbench.ts:71/77](../src/state/workbench.ts#L71)，预览实时读取路径：[main.ts:82–86](../src/desktop/main.ts#L82)。这在普通文件浏览中合理，但不能当作历史交付或审批版本证据。

另有两条遗漏：工具桥只为 write/edit 登记路径，Bash 生成的文件没有产物发现：[task-host.ts:25](../src/runtime/task-host.ts#L25)；路径先存在成员执行闭包的内存数组，只有 `runTask` 正常返回后才进入消息：[main.ts:128–135](../src/desktop/main.ts#L128)、[conversation-session.ts:85–90](../src/runtime/conversation-session.ts#L85)。因此写文件成功后模型超时/停止/异常退出，文件可能留在空间里，却没有对话交付链接。

建议：工具成功时先独立登记产物事实，任务失败也保留可用的部分结果；对 Bash 产物提供明确登记协议。需要审阅/发布的交付记录固定版本或 hash，区分“当前文件”和“当时交付版本”。R07 中用户指定产出子目录也应进入配置，目前只有 prompt 固定 `outputs/`。

### F09 · P2 · 长历史截断会悄悄丢掉业务约束与来源

**调度实测 E07 + 静态确认。** 在初始“未经确认不要发布”之后加入 71 条构造消息，新任务 prompt 已不含该约束。模型只接收最近 70 条、最后 65000 字符：[conversation-session.ts:82](../src/runtime/conversation-session.ts#L82)。不是上下文超限后明确阻断，而是静默删除。

反例：早期确认过禁用来源、待补材料、审批方式，后续继续时不再可见。群内分工与系统回执也消耗消息配额，未必需要很长的人类对话。所有消息按 `speaker: content` 拼成一段文本，内容里的换行和“你:”没有可信消息结构；这是来源辨识风险，未做模型攻击成功率验证。

建议：预算内截断可以保留，但任务约束、批准记录和重要交接事实应独立持久化；传入可溯源摘要和缺失上下文说明。消息保留可信角色与来源，导入资料不能形成用户指令。前置审批仍必须由 F03/F06 的执行规则兜底。

### F10 · P2 · 建队重试校验与真实成员状态会分离

**调度/存储实测 E06。** 同名、同成员名但新职责/新目标的 create_team 返回旧职责旧目标；手动移除一名成员后，再以原两人名单重试，返回成功但实际群成员只有一人。

证据：[workbench.ts:40–44](../src/state/workbench.ts#L40) 只比较创建时 `teams.roster` 的名字；[update:63–64](../src/state/workbench.ts#L63) 更新 conversations.members 和 teams.name，不更新 roster。协调人与成员职责可编辑，角色名字还嵌入自由文本，进一步增加漂移。

不覆盖用户已编辑职责是正确的；问题是静默复用不能解释“输入是否已应用”，且创建快照不再反映现在的成员关系。

建议：明确返回 reused/currentState/differences；精确重试与修改团队分开处理。对当前成员关系做一致性校验，保留创建快照时应明确它只是历史。验收覆盖改名、增删成员、修改职责之后的重试。

### F11 · P2 · 持久化只覆盖部分状态，恢复无法判断已做过哪些动作

**静态确认，故障后果为风险推导。** 根任务和成员消息分别在两个 SQLite 文件里：[main.ts:61–62](../src/desktop/main.ts#L61)。`session.human` 写消息/子任务后才 `taskStore.start`：[main.ts:123](../src/desktop/main.ts#L123)；交付消息与 jobStatus 也是独立写入：[conversation-session.ts:87](../src/runtime/conversation-session.ts#L87)。没有跨记录的统一提交协议。

崩溃窗口可能出现消息与根任务记录不对应、已有交付但成员中断、文件已保存但尚未登记。启动统一标 interrupted 是保守行为，值得保留，但不能还原副作用事实。工具事件只保留内存，最多 200 条且重启清空；group_jobs 也没有开始/结束时间、工具回执、批准版本或恢复检查点。

建议：先做最小追加事件账本，将根任务/成员/工具意图/结果/产物关联起来；同库事务或明确的恢复对账协议解决部分提交。恢复先检查事实再决定重做，不应仅靠用户再次发送原话。完整长期恢复是已列出的 T13，本项揭示现有继续开发必须保留的信息，未宣称 T13 已完成。

### F12 · P2 · 存储查询和状态轮询存在规模增长风险

**静态确认，未进行压力测试。** SQLite 操作同步运行在 Electron 主进程；messages.conversation、group_jobs.conversation 未建查询索引：[workbench.ts:8–14/69/73](../src/state/workbench.ts#L8)。renderer 每 600ms 获取全状态并重新生成任务列表：[renderer.ts:68–69/102](../src/desktop/renderer.ts#L68)，state 内多次读取成员列表：[main.ts:38–44](../src/desktop/main.ts#L38)。

多群历史积累后，即便返回 LIMIT 100/80，缺索引也可能扫描大量不相关记录。轮询与同步查询会挤占主进程处理任务和停止请求的时间。这里没有测得延迟数字，不声称当前数据量已卡顿。

建议：先为已知访问路径加索引、明确游标分页，再按事件推送增量，避免每次状态请求重复全表成员读取。用构造的多会话数据测停止响应时间与查询耗时，达到规模阈值后再考虑移动数据库线程。

## 6. 建议的修复顺序与验收门槛

建议继续沿 requirements → design → implementation → testing 推进，先写下面每一项的具体失败不变量，再实施；不要先扩大 Agent 数量或包装更多发布工具。

1. **先收紧执行控制：F01/F02/F03。** 空间外真实文件不可因硬链接被触达；停止后无残留副作用；未经对应业务授权不能外发。必须以实际工具、后代进程和本地提交站点验收，提示词和单元测试不能替代。
2. **统一任务语义：F04/F05/F06。** 人工修改可在下一副作用前生效，消息顺序保持，根状态反映未确认项，前置受阻不派发依赖任务，批准绑定版本。
3. **补账号、产物和记录：F07/F08/F11。** 明确账号共享范围与页面控制权；部分失败也有产物记录；历史交付固定版本；能回答“谁在什么授权下对哪个版本做了什么”。
4. **完善长期使用：F09/F10/F12。** 保留关键约束，建队变更可解释，消息索引和分页明确。再落实独立成员模型、生图、上传下载和干净安装。

完成这些门槛后，才适合扩大到“真实团队、真实账号、长期业务”的验收。视觉后置是合理顺序；这里需要前置的是功能语义、执行边界和失败时的可控性。
