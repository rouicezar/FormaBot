# S1 任务控制：群消息归属与依赖收敛

## 当前路由事实（修复前基线 f9a693e）

`main.run-task → startTask → ConversationSession.human → resolveAttention → enqueue → runTask`。
`resolveAttention` 先判断全员，再匹配指定成员，最后才回退到协调人/选择器/首位成员。正确识别的 @ 不调用协调人模型，也不调用 assign_tasks。成员接收的是完整原始消息。

`assign_tasks` 是模型按需调用的分工工具，有协调人时只有协调人可以使用；普通成员仍可通过群消息 @ 同事协作。主管汇总只在实际 assign_tasks 派发后触发。不是每个群任务都有主管前置/后置轮次。

问题：识别结束边界漏掉问号、分号等标点；未命中会静默回退。模型提示词没有突出用户直接指定的任务归属。依赖按成员 ID 关联，responded 也释放下游，异常/静默/多级依赖不收敛，循环未拒绝。

## S1a 本片需求与设计

> 用户在实现期间进一步明确全员静默分析模式。下述 S1a 只修复已有 @ 识别和依赖错误，不能作为新群聊模式验收。后续 S1b 必须替换默认协调人路由与固定主管汇总，不将仅目标成员收到消息的旧测试当作新模式通过。

- 保留直接 @ 和全员直达，统一中英文标点/全角 @ 识别；不增加路由 Bot，不调用模型决定一个已明确 @ 的接收人。
- 指定成员基于完整消息与职责回应、执行或说明限制；保留消息里明确的通知/协作要求。纯通知仍可按用户意思不回复，不对所有 @ 粗暴禁用静默。
- 依赖解析为本次实际任务 ID；先验证整批依赖、唯一指向与无环，再原子写入任务队列。重复分工调用返回原收据，不重复创建。
- 只有 completed 放行后继；responded/silent/blocked/failed 均将后继逐层标 blocked；成员异常、启动异常和队列耗尽都不能留下 held 后根任务 completed。
- 本片不宣称修复在途角色/指令版本、产物、浏览器审批或完整重启恢复。依赖的持久恢复是后续 S1 切片，现有数据/授权不迁移或重置。

## 验证与交付

先增加会失败的调度测试；再修复并跑全套检查。使用已配置真实模型，在新隔离工作空间/测试群验证自然语言 @ 成员：第一个且唯一执行者为目标成员、主管无中转、真实文件由目标成员交付；另验证前置失败时下游未执行。

每片构建并提供具体 App/提交/结果，自动验证不冒称用户验收。后续按任务控制→可信交付→浏览器与审批→受控内测→正式发行推进，正式发布仍需对应账号/签名/托管授权。

## S1b 最新群聊模式

1. 用户及 Bot 的业务消息成为带稳定 ID、来源/上游、群范围的事件。全体群员收到，系统状态日志不触发模型。
2. 每个成员独立进行不公开的参与判断；不使用固定委派 Bot 或另一模型替所有成员决策。只有决定有信息增量或承担工作时进入公开回复/执行；静默不留占位气泡或思考文本。
3. @ 固定直接责任人；其他成员是观察参与者，不抢主任务。未 @ 的消息由成员根据职责自主判断，不默认给主管。用户定义的管理职责保留，但不是路由特权。
4. 执行前登记工作认领与上游，防重复执行；结束时交付文件及回执，投递给上游。取消、职责版本、依赖结果由宿主控制。
5. 事件对成员只投递一次；回复作为新事件，不把已处理的同一内容反复唤醒。区分讨论、执行、完成通知，控制反馈环；不能靠所有人轮流跑一遍完整任务冒充静默判断。
6. 验收：@ 编辑时所有人有判断记录而只有编辑承担主任务；无 @ 的写作问题由编辑自主参与；普通成员可直接向同事交接；纯通知无刷屏；交付回到正确上游；多轮不会循环/重复写文件。全部以自然语言、真实模型和打包 App 验证。

截至 S1a，这组模式尚未实现，不能宣称已经切换。
