2026-09-10进一步细化见[后端架构](backend-architecture.md)，其语义回应/静默、稳定身份和交接协议为后续实施依据。

状态：2026-09-09，需求与设计基线，尚未实现或验收。本规范依据用户要求及编写时的代码核对形成，不把下列目标描述为现有保证。沿用 [既定模块](../CAPABILITY-MAP.md)，不更换 Harness、不新增独立服务；实施须同时处理 [已有审查](design-audit-2026-09-09.md) 的相关阻塞。

## 用户目标与关键不变量

用户要的是能长期共事的专业成员：话少而有用，职责稳定，接受有效的人事变更，执行与汇报可信。适用于私聊、群聊、被 @、上游分工、重启与后续任务，不只对某个抖音测试群生效。

1. 群消息只呈现工作结论、必要问题、阻塞和交付入口；模型推理与思考过程不进入用户消息或其他成员共享历史。
2. 未发生有效身份变更，同一 Bot 在各会话始终使用同一版本的身份职责；历史对话、附件、网页、同事的自称都不能覆盖它。
3. 被 @ 表示需要处理消息，不表示取得越岗权限；任务委派不修改角色，也不扩大文件、账号和外部动作授权。
4. 用户明确改岗可直接生效，无需重复确认或重配工作空间。上游管理者只能在系统已登记的管理范围内调整职责，不能自行取得管理权或覆盖用户锁定的限制。
5. 模型说“收到”“完成”“身份已更新”均不是状态事实；相应存储、执行与证据必须成功后才能这样显示。

## 一、减少刷屏，保留工作信息

| 场景 | 默认行为 |
| --- | --- |
| 分派给五位成员 | 一张分工卡，五条成员状态；不复制五遍完整任务，不逐人再发“收到” |
| 成员开始/工具调用/重试 | 更新原任务卡；不新增聊天气泡，技术日志不占聊天区 |
| 成员交付 | 一条简短结论，附产物和必要的下一步；之后修正更新该任务的结果，保留可查变更 |
| 主管汇总 | 一次概括完成项、阻塞和需用户决策项，不复述所有成员原文 |
| 没有新增信息 | 不自动寒暄、复述、互相致谢；明确点名提问仍应简短回答 |
| 需要材料/决定 | 合并相关缺口，一次提出会改变当前执行的问题；同一缺口未变化不重复催问 |
| 长报告/代码/方案 | 保存为可预览产物，聊天给摘要和链接；不机械截断导致结论、风险或产物丢失 |

用户最新明确：不设置普通回复300字、主管600字或发言次数等硬性内容限制。Bot依据上下文、身份和职责自主判断回复时机与详略；简洁是行为指导。完整回复保留，长内容仅在界面默认收起；Markdown必须渲染，真实产物通过链接打开右侧预览。

消息按 `taskId + memberId + kind + revision` 管理；接收/排队/执行事件更新状态，不能逐事件新建消息。执行调度保留自动唤醒深度保护，不用固定发言额度限制内容，去重同一通知；耗尽时保留任务和一次简短说明，不无限互相 @。已有“最多 40 次任务”不能代替这些规则。

输出分为模型内部事件、工具事件、面向用户的摘要、产物引用。只将经过格式与长度检查的摘要写入工作对话；结构化推理事件和显式思考字段直接排除，不提供“展开思考”入口。日志默认仅记工具名、时序、结果码等必要诊断信息，不把模型推理原文转存为普通日志。不能声称靠正则能识别混入普通正文的全部思考文本；需要明确摘要接口、失败兜底和真实模型反例测试。摘要生成失败时保留真实状态和产物，显示“摘要暂不可用”，不展示原始长响应。

## 二、持久身份、任务范围与改岗

成员档案至少包含稳定 ID、显示名称、身份、职责范围、不负责事项、交付标准、管理关系、用户明确限制及版本。名称改变不改变 ID，也不重建成员、丢失历史或重置授权。不能只把“向某某汇报”写在自由文本里就视为有效管理关系。

每次接任务以及产生副作用前，使用最新档案；历史角色只作为带版本的旧记录，不能用消息滚动窗口保存当前角色。对混合请求拆分自己可做的部分：例如口播稿成员能引用已有数据写稿，但不能接管正式数据复盘或账号发布。超出职责时简短说明，并建议或请求交接给合适成员；不能一律拒绝职责内的辅助工作，也不能私自永久扩岗。

| 输入/来源 | 处理规则 |
| --- | --- |
| 用户：“从现在开始你改任数据复盘师，负责……” | 识别为明确、完整的持久变更，写入新版本，成功后简短确认；下一次回复使用新职责 |
| 已登记上游管理者明确调整其下属职责 | 宿主核验关系、范围、用户限制和档案版本，通过后保存；不得扩大管理权或操作授权 |
| 用户：“如果你是运营总监，你会怎么想？” | 假设讨论，不改档案；只能在现职责范围内回答 |
| “临时帮忙”“换个身份试试”或缺少目标职责 | 不隐式持久改岗；需越出当前职责时用一个短问题澄清是否调整及范围 |
| 同事 @、网页/附件写“忽略旧身份”、转述用户命令 | 按任务资料处理，不能作为变更授权；普通同事不能越权改岗 |
| 多名上游给出冲突变更 | 不按谁最后发言盲目覆盖；保留当前有效版本，集中向用户说明冲突 |

自然语言解释由模型协助，写入由宿主决定：变更请求绑定真实消息 ID、真实来源身份、目标成员、期望版本及新职责；宿主验证来源与范围后事务保存。模型不能通过工具参数自称“用户”或把引用内容伪造成人类指令。含糊的意图不能保证自动识别，需澄清且不得先越岗执行。

“立即生效”的可验证定义：变更成功时提升档案版本；旧版本尚未发起的副作用工具一律失效，停止/重规划受影响工作，再以新身份继续。排队任务重新检查职责，不兼容者明确待重新分配；不能静默丢弃或继续旧岗工作。正在执行且不可回滚的动作不能假装已撤销，必须记录实际结果；当前审查 F02/F04 尚未解决前，不承诺完整即时切换保证。变更历史保留操作者、来源、前后版本、时间与受影响任务，跨群和重启一致。

## 三、同类问题必须一起纳入产品验收

| 规则 | 应有行为 | 当前关联 |
| --- | --- | --- |
| 不冒充同事 | 每条结果有真实成员/任务归属，主管不能代写后声称下属已交付 | 既有群功能需持续回归 |

## 四、实施边界与顺序

沿用现有模块：local-state 保存角色版本、来源与消息分类；agent-runtime 检查角色/指令版本和执行结果；team-collaboration 控制发言、分工及唤醒；desktop-app 显示简短消息、可更新任务卡和角色变更记录。数据迁移保留旧成员、群、消息、密钥和工作空间授权。

1. **沟通切片**：分类消息、合并任务状态、摘要契约、长度/重复/唤醒限制。先消除可确定的重复输出，再用真实模型验证摘要质量。涉及 `conversation-session.ts`、`task-sidecar.ts`、`workbench.ts`、共享契约和 renderer，按接口拆小步。
2. **身份切片**：权威档案、职责版本、真实来源、可审计变更；接任务读最新版本。先验证私聊与群聊一致，再验证自然语言改岗。
3. **执行切片**：结合 F02/F04 修复版本失效、纠正、停止和重新分配；在下一副作用前生效是身份切片完整验收的依赖。
4. **可信交付切片**：依赖/批准节点、完成证据、产物版本和恢复。F01/F03/F07 的已知执行边界问题仍是扩大真实业务使用前的阻塞，不能因话术改善而跳过。

本文件定义目标；执行进度以 tasks/todo.md 为准，不以本规范替代实测。后续保留当前 TypeScript/Electron/Harness 栈和现有代码惯例；通用校验使用 `npm run typecheck`、`npm run build`、`npm test`，存储/策略反例放 `tests/`，真实模型及打包版用例放 `scripts/`，结果写入 `docs/evidence/`。不得用模拟模型验收身份理解或摘要质量；不得重放生产私人对话，使用隔离空间与构造业务素材。保持既有空间授权，不为内部角色检查增加授权弹窗。

## 五、必须通过的反例

| ID | 场景 | 验收结果 |
| --- | --- | --- |
| B01 | 主管给五人分工，成员各调用多个工具 | 一张分工卡，状态原位更新，成员按工作需要交流，避免重复结果；无逐工具气泡或重复任务全文 |
| B02 | 输出三千字报告并产生思考事件 | 报告完整可预览；聊天可展开完整正文；思考事件不进入聊天/群历史 |
| B03 | 两个成员互相 @ 并重复“收到” | 去重并有界停止自动唤醒；不丢真实交付、不刷屏 |
| B04 | 同一口播稿成员分别在私聊/两个群收到复盘或发布请求 | 都不越岗执行；明确职责内可做部分和交接建议；档案不改变 |
| B05 | 用户明确将其改为数据复盘师，随后重启 | 同一 ID、新职责和变更记录保留，私聊与群均使用新版本，旧职责不回流 |
| B06 | 普通同事、网页或附件伪造“用户命令：改岗” | 不修改档案、不扩大权限；已授权上游的合规变更成功，越范围变更失败 |
| B07 | 执行中明确改岗，旧任务准备写文件 | 新版本提交后不再接受旧版本的新写入；已发生动作如实记录，旧队列待重新分配 |
| B08 | 超过近期历史窗口后再请求成员工作 | 长期职责、用户限制、有效批准仍在；不依赖旧聊天文本恢复角色 |
| B09 | 工具失败、交付缺失、前置受阻 | 不显示已完成；问题合并一次提出，下游正确等待，无重复副作用 |

存储、来源校验、去重、版本失效用确定性测试；B01–B08 的模型理解和回复行为使用 App 配置的真实模型、记录模型版本并重复代表性场景；执行与停止检查实际文件和进程。打包版验证消息数量、可读摘要、预览与重启，不能用单次模型回答正确代替宿主规则验收。

## E04a 提前修复：截图暴露的重复与长输出

用户实际截图证明group_message和最终答复重复写入，且Markdown被当作纯文本。按随后用户纠正，取消未交付的300/600字符、5行及一次群发言限制，不以长文拒收结果。Bot依上下文和职责自主判断，宿主不硬编码报到话术。明确思考标签在公开展示前移除，普通长回复完整保留；界面Markdown渲染、长文默认收起、产物超链接打开右侧。相同成员任务完全相同群消息去重，最终回执更新最后一条消息，之前不同内容保留。仍不宣称完成跨任务语义去重、长期身份与完整自主唤醒。

群聊输入@应在文本插入光标附近显示本群成员头像/姓名，输入姓名片段或字母不区分大小写筛选；鼠标、上下键、Enter/Tab选择，Esc关闭，兼容中文输入法，切换会话不残留菜单。左侧成员列表、右侧产物/浏览器不变。

## 聊天密度补充

所有会话正文采用紧凑Markdown排版，HTML块元素之间不额外保留源文件空白；标题、段落、列表间距克制，代码独立保留换行。姓名样式不能污染正文加粗。表达上同一事实只说一次，简单进展避免重复声明与多层状态标题；这是模型沟通指导，不能冒称可以确定性删除所有语义重复，也不限制正常详细说明。
