# FormaBot 仓库、开发进度与上线准备审计

审计日期：2026-09-12。产品代码基线：`e40838e4495c05d40d6e0c0880a9148439e7938e`，分支 `main`。本次仅新增审计报告、反例脚本和证据、更新审计入口；不修改产品实现、不重置用户数据、不发布。

## 1. 结论与决策建议

**仓库的 Git 工作树是干净的，但产品工程状态并不干净。功能已经从早期原型推进到可试用的本地 AI 团队工作台，仍不能按现有需求宣称正式上线就绪。** 当前最大障碍不是缺少更多按钮或更换 Harness，而是执行权限、任务状态、交付版本和验收证据没有形成一致的闭环。

这轮推进有真实价值：稳定身份、角色版本、审批入口、记忆、跨会话委派、成员模型绑定、可选产出目录、文档建队及网页图像输入都已有实现。不能沿用 9 月 9 日“几乎只有原型”的认识，也不能把 todo 中的“主线全部落地”“live 全通过”理解成对应完整验收已关闭。

**建议立即冻结新增能力，先完成三组修复：任务与依赖、可信交付、浏览器与审批。之后用限定范围的 macOS arm64 内测版验证真实用户闭环。** 生图、通用 MCP/插件/Skill、自动更新继续保留在需求中；若要后置到首发之后，需要明确修订首发范围，不能悄悄删除。

不建议此时重写应用或更换执行内核。已有框架足以支撑下一轮整改；更换框架不会自动修复下文的宿主错误。

## 4. 对产品的更新认识

FormaBot 当前应被定义为：**用户通过一个默认通用助手，在授权的本地工作空间建立持久团队，以私聊或群聊布置工作、介入执行，并在同一对话获得可核验的本地成果。** 浏览器是研究与执行工具，成员身份与会话是长期组织方式，工作空间是默认成果位置。

它不是固定内容运营五人模板；文章五岗、视频五岗只是业务夹具。用户后来加入的需求已经把产品从“多人聊天壳”推进到“有长期身份、记忆、委派和人工控制的执行工作台”。验收主线应围绕这一点，而不是不断增加阶段编号。

当前实际架构：Electron 持有配置、SQLite 与浏览器；每会话一份内存任务队列；成员轮次启动独立 sidecar/Harness；模型工具经令牌化本地桥回到宿主；文件/Bash 进入 macOS sandbox-exec；浏览器使用一个工作空间共享的 WebContentsView。并发发生在会话层，群内成员仍依次执行，账号/页面仍共享。

应保留的基础：密钥系统加密、主 IPC 来源校验、空间身份授权、固定工具白名单、原生工具关闭、建队事务、稳定作者 ID、迁移版本、重启不盲目重放、真实模型脚本。这些基础值得继续建设。

产品体验的新建议：默认助手负责“理解需求—确认必要信息—组织团队—交付”，专业成员负责执行；普通用户不必理解 job、root、工具名或 DAG。审批应让用户看清“谁、在哪个账号、要做什么、影响什么”，任务应让用户看清“谁在做、缺什么、结果在哪”。

## 6. 新发现与重新确认的问题

优先级：P1 为扩大真实业务/内测前应修；P2 为首发前应处理或明确限制。以下不声称利用了真实账号或证明模型会主动触发越界。

### N01 · P1 · 依赖调度没有遵守完成前提，终态不收敛【本轮调度实测】

[conversation-session.ts](../src/runtime/conversation-session.ts) 的 `releaseDependents` 只排除 blocked/failed，因此 responded 也被释放，并把指令改成“前置任务已完成”。执行异常进入 catch 时根本不调用依赖收敛；silent 提前 continue 也跳过。循环依赖没有校验，多级阻断只传播一层。

本轮实际结果：A 仅 replied/responded，B 仍执行；A 抛异常，B 永久 held；A silent，B held；A↔B 循环时只运行主管汇总、根状态 completed 而 A/B 都 held；A blocked→B blocked→C 仍 held。前置关联还是 member ID，不是具体 job ID，同成员多任务可能错误释放。

修复：任务 ID 依赖图、入队时拒环、仅通过明确完成条件才释放、失败/停止/静默逐层收敛、根终态必须覆盖全部子任务。新增这些反例，不能只补已有 blocked 正常用例。

### N02 · P1 · 产物快照保存与读取使用不同 ID【静态确认】

[main.ts:256](../src/desktop/main.ts#L256) 保存到根任务 `id` 的 artifacts 目录，名称哈希也用根 ID；[conversation-session.ts:179](../src/runtime/conversation-session.ts#L179) 发布消息使用成员 `job.id`；预览按消息的 taskId 查快照。正常任务的根 ID 和成员 ID 不同，旧链接找不到快照后回读可变工作文件。

同一成员多次 write/edit 同一路径又被 `!artifacts.includes(path)` 跳过，首次写入后不再更新快照和账本；即使统一 ID，也需要明确“每次交付版本”还是“最终交付版本”。图片快照还先执行 `bytes.includes(0)`，普通 PNG 含零字节，会在 MIME 判断之前回退。

修复：一份稳定 artifact/version ID，消息、快照和账本都引用它；正文和关联资源形成同版本集合；快照失败显式报错。实测必须走真实 write→edit→发消息→改源文件→点旧链接，而不是预置快照。

### N03 · P1 · 汇总的只读限制可由 Bash 绕过【本轮真实 Bash 实测】

[task-host.ts:19](../src/runtime/task-host.ts#L19) 只拦 write/edit，仍放行 bash。新增探针在 `readOnly:true` 下执行 `printf audit > summary-wrote.txt`，文件真实写入成功。浏览器/建队等其他副作用也没有统一只读策略。

修复：按任务模式决定能力集合，并在文件执行层限制写权限；汇总只拥有读取已有交付和发布汇总所需能力，不能仅隐藏两个工具名。

### N04 · P1 · 改岗/中途纠正没有使旧执行失效【静态确认】

`startTask` 在运行时收到消息只 `session.human(...)` 追加队列；工具桥授权回调只检查空间，未核对 job 的 roleVersion、instructionVersion 或批准版本。修改职责不会取消当前工具权限。已有 correction 测试证明“旧任务保留旧版本、新任务使用新版本”，没有证明“旧版本副作用被拒绝”。

此外系统提示词前段仍写“当前尚未接入持久改岗工具”，群聊分支才追加 request_role_change 指导，私聊与群聊指示不一致。

修复：宿主维护执行版本/取消令牌，副作用提交前复验；将“补充下一任务”和“纠正当前任务”明确建模。删掉过期提示词，不把提示词当版本门禁。

### N05 · P1 · 浏览器停止和人类接管不覆盖页面生命周期【本轮浏览器实测 + 静态确认】

[browser.ts](../src/tools/browser.ts) 在单次工具结束的 finally 移除 abort 监听。页面仍存活；本轮回环页面在 open 返回后 abort，延时 POST 仍到达测试服务器。主进程 stop-task 没有独立关闭/冻结该任务页面。

租约只有工具栏导航、选择和截取路径 hold；未订阅嵌入网页的普通鼠标/键盘输入。因此“用户在页面里输入就接管”没有实现，固定 60 秒后也可自动归还。并发会话还共享同一个页面，只按单次动作串行，A open→B open→A click 仍可能点击错误页面。每空间共享 Cookie 不能算双账号隔离。

修复：页面归属任务/账号的会话租约、显式接管/归还、所有页面输入更新状态、取消覆盖页面后续活动。同一账号/页面的整段操作需串行，而不仅单个 call。

### N06 · P1 · 动作审批粒度与 R30 不符，敏感输入旁路控制【静态确认 + 策略实测】

规则仅匹配 host+click/fill；批准窗不展示 selector、填入内容、账号、内容版本和具体影响；“始终允许”扩大到全站同类动作。open 永远 allow，URL 请求和页面脚本仍能产生出站行为。沙盒允许 localhost:*，不能把“禁止直接外网”描述为“完全无法外发”，本地代理/服务也是边界。

密码分支先 fieldType→等待 securePrompt→直接 secureFill，没有经过 browser.call 的队列、租约和 abort 检查，也没有复验页面 URL/账号/元素。等待期间导航或停止后，输入仍可能落到变化后的页面。只识别 type=password，未覆盖 OTP 等敏感字段；secure-prompt IPC 未核验 sender（当前无证据证明普通网页可直接调用该 IPC）。

修复：批准对象绑定任务、页面/账号、动作参数和内容摘要，执行前再验证；敏感输入走同一受控事务；未知动作不默认为已批准。先用回环测试站点覆盖导航、取消、过期和窄规则。

### N07 · P1 · 图像材料的会话/任务归属错误【静态确认】

[main.ts:190–205](../src/desktop/main.ts#L190) 对当前 conversation ID 调 `memberModel`，该方法只允许 bot；在群聊带图会抛“Bot 不属于当前工作空间”，未解析实际接收成员。运行中的新图像被 startTask 的追加分支忽略；闭包中的首批 images 则传给这轮之后的每个成员任务，包含跨会话委派任务，而不是按消息/任务分配必要材料。

材料在 runtime、忙碌锁和授权等检查之前清空；发送被拒绝也丢卡片。pick/capture 完成时取“当前选中会话”，未固定开始时会话；切换会话后可能把原页面材料加到另一个会话。截图删除仅删偏好记录，磁盘文件没有生命周期回收。

修复：附件属于一条可持久消息，任务引用经批准的材料 ID；接收成功后才清草稿；按实际执行成员判视觉；跨会话只分享明确批准的包，取消/失败保留材料。

### N08 · P1 · 选区监听器退出后仍运行，选择动作可能触发网页行为【本轮脚本实测 + 静态确认】

PICK/CAPTURE 使用匿名 addEventListener，cleanup 只删样式/覆盖层，没有 removeEventListener。运行原 PICK 脚本再退出，留下 3 个监听器；两轮后 6 个。回调没有 active 检查，普通页面点击仍可能被旧回调处理。

点击选择只 preventDefault，不阻止网页 click 处理器；截取模式没有屏蔽 click 默认行为。选择“发布”按钮附近内容可能同时执行网页业务行为。页面脚本还可直接写 `window.__formabotPickResult`/CaptureResult；目前没有来源验证。特殊 iframe/DPR/缩放需要 E12c 真正覆盖，不能由普通 DOM 合成事件验证推断已全部可用。

修复：选择模式独立 overlay/isolation、可撤销监听器、阻断选择时的页面动作、任务/页面版本化结果；退出、导航、取消和再次进入都做真实事件回归。

### N09 · P2 · 交付“机器核验”只检查现存文件非空【本轮实测】

账本存 sha256 但 verifyDeliveries 不比较哈希；本轮将登记的 original 改成 changed，仍无错误。零登记同样返回无错误，所以“要求交文件却没有任何文件”的任务也可以 completed。Bash 产物不自动登记；失败路径只写系统失败消息，不保证已产生文件可在对话访问。

来源门只检查一个 URL 字样和一个日期，不核验链接真实性、出处与论点对应关系；这可作为格式下限，不能称“研究结论已机器验证”。

修复：为文件任务保存期望交付项，验证版本、文件和结果；纯问答可以无文件。将 submitted 与用户 accepted 区分，保留失败中的有效产物。

### N10 · P2 · 恢复、超时和并发锁不是完整任务生命周期【静态确认】

依赖仅存在内存中，重启 SQL 只处理中断 queued/running，held 留存；“重新入队”只是把旧指令填回输入框，不是检查点恢复或幂等重放。TaskTimeout 在 session 内被普通 catch 转 failed，主进程期待的 interrupted 分支通常接不到，重试按钮又只在 interrupted/stopped 出现。

跨会话忙碌判断扫描 activeTasks 的原始会话名册；跨会话 handoff 入队未统一取得执行成员锁。启动的 await probe/授权之前没有原子占位，也需验证并发启动竞态。暂未执行这些竞态的完整 UI 反例。

修复：持久化 task/job 状态和依赖、原子 Bot/文件/页面资源锁、保留超时类型、重试时展示已执行副作用并防重复。不建议首发自动重放外发任务。

### N11 · P2 · 文档建队的成功声明超出 A14 覆盖【静态确认】

createTeam 对同名团队只比较成员姓名，职责/目标变化不报差异也不应用；“重复建队幂等”会吞掉需求修订。业务审批节点仍在角色文字里；创建前的一次批准不等于持久流程里的选题批准、审核与发布节点。文档来源只留最近 20 条 preference，未形成文档版本→建队操作→团队版本的稳定关联。

修复：区分重试同一操作与用户修改团队，显示差异后版本化更新；文档的流程节点以最小明确数据结构存储并由宿主执行。

### N12 · P2 · 历史可用性、数据迁移和代码可审查性欠账【静态确认】

messages 只返回最近 100 条、jobs 最近 80 条，界面没有向前翻页；持久保存不等于用户还能查看早期成果。记忆全部注入，无预算；600ms state 轮询反复执行列表/偏好查询，索引并不能证明规模验收完成。

迁移 v1/v2/v3 的升级分支在备份逻辑之前 return，只有旧 v0 路径 VACUUM INTO；不能笼统宣称每次迁移都有快照。某些读取测试直接打开 WorkbenchStore 构造器，会顺带把运行中任务标 interrupted，不是只读观察。

源码行数具有误导性：renderer 352 行约 45 KB，main 389 行约 37 KB，session 216 行约 26 KB，最长逻辑行超过 2,000 字符。建议先格式化涉及修复的模块，再按调度、审批、附件、产物职责切边界；不要为了“架构化”拆出多层空壳。

## 7. 工程流程审计：哪些是调整，哪些是偏离

**有授权记录的调整不算偏离。** plan 的“2026-09-12 用户授权目标模式”明确允许不逐片等待手测；另有 UI 顺序调整记录。因此不能拿旧规则断言连续开发违规。用户手测历史仍不能补造为全部通过。

实际流程问题是：

1. **多个当前真相源互相冲突。** README/status 仍称单模型、串行、选区未实现；todo 顶部 E03–E09 待实施，后部却称全部落地；main 已合并，后部仍反复写“未合并”。新授权只追加在 plan，中旧规则未标失效。
2. **小规格通常存在，但不是每项都覆盖失败语义。** 阶段拆片和提交记录总体存在；N01 等表明实现围绕成功样例推进，终态/失败/竞态设计不足。不能仅凭同一提交有 plan 和实现，证明需求设计先于开发被评审。
3. **验证层级被混合。** manual-sim 标“11/11 通过”，但第 11 项依靠单测与历史 live，部分条目 stub 原生对话框、直接注入数据库或合成 DOM 事件。自动化有价值，却不能替代用户认可，也不证明端到端自然操作。
4. **测试绕开真实缺陷。** 快照测试预置正确路径，关联资源脚本把源与快照写成同内容且没有断言版本差异；故无法证明真实交付不可变。源码布线测试也不能代替业务行为测试。
5. **发行证据不可稳定定位。** 多个包都叫 0.1.0，同一路径覆盖；没有统一 release manifest、提交号、测试摘要、包摘要；很多证据只在忽略的 .tmp。
6. **安全门槛被局部实现替代。** E02/E03 被标可推进，但停止、在途改岗、审批版本和账号范围未闭合，随后已加入并发、委派、截图等放大边界的能力。

这不是“没有工程流程”，而是**流程已经有文档和脚本，但缺少防止局部通过被升级成整体完成的验收约束**。

## 9. 让产品尽快上线的推进方案

先把“受控内测”和“完整需求正式版”分开决策。当前正式基线 A01–A24 包含生图、平台操作、扩展能力和更新，不可能仅修几个 bug 就宣称全部上线完成。

| 次序 | 独立交付 | 必须通过的验收 | 前置 |
| --- | --- | --- | --- |
| S0 | 当前范围/状态统一，构建身份可追溯 | 一份当前状态表；历史明确归档；App 显示版本+commit；测试日志对应包 hash | 本报告评审 |
| S1 | 任务调度和控制修复 | N01 全部反例变为安全结果；在途改岗旧动作拒绝；无 held 悬挂；超时/停止可追踪 | S0 |
| S2 | 真实交付闭环 | write→edit→完成→修改原文件→旧链接仍是正确版本；失败保留有效交付；汇总无法写文件 | S1 |
| S3 | 浏览器/审批/附件边界 | 停止后无迟到动作；人工接管不被抢；审批绑定页面/内容；切会话/忙碌/群聊/补图不串不丢；退出选区无监听残留 | S1；与 S2 可分别交付，不扩真实账号 |
| S4 | 受控内测候选包 | 新 macOS 用户/干净目标环境安装；旧数据升级；自然语言完成下方三条业务闭环；用户手测记录 | S1–S3 |
| S5 | 按首发范围补齐发行 | 签名公证、版本/更新策略、故障回滚、依赖许可清单、发布授权 | S4 + 范围决定 |

建议首个内测范围：macOS arm64、已验证的一个服务商及有限模型、单工作空间、本地文件交付、网页资料研究、持久团队。对浏览器账号并发和外发动作实行明确限制；限制必须由执行层实施，不能只在文档写“不建议”。

**建议后置但未擅自取消的能力**：通用 MCP/插件市场、自动更新、生图、多平台上传发布、第二服务商。若用户认为生图/平台发布就是首发核心价值，则必须保留并安排真实凭据验收，不能换成“研究助手版”冒充原目标完成。

三个自然语言内测闭环：

1. “读这份业务文档，建一个适合我的团队，给我本周方案，保存到指定文件夹。”核对真实成员、职责、审批、目录、文件与重启。
2. “请根据我选中的网页内容做分析，先给审核员检查，再给我最终报告。”核对材料范围、依赖、来源、失败处理和旧版本。
3. 任务执行中说“前面的要求改了，停止发布，只保存草稿”，然后中止/重启。核对旧动作确实停止、未对外提交、剩余任务可解释、数据不丢。

不建议现在给出确定上线日期。先让 S1–S3 反例全转安全、跑出 S4 的真实用户结果，才能估算剩余发行工作；仅按代码行数或 74 个绿灯给时间承诺没有依据。

下一开发切片建议 **S1/N01：依赖任务状态收敛**。范围小、已存在清晰反例、可以独立构建交付；随后修在途版本与产物一致性。此报告不自动启动开发阶段。
